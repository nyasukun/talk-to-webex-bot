# トラブルシューティング

まず「ログ」を開き、分類や「注意・エラーのみ」で絞り込んでください。「診断テスト」にはWebexへ送らないマイクテストとローカル環境診断があります。ログはこのMacのアプリ用フォルダ `diagnostics/events.json` に直近500件を保存します。処理の種類・時刻・件数・秒数・話者類似度などを記録し、会話本文・宛先・API Key・画像・録音は記録しません。コピーする前に画面で内容を確認できます。

| 症状 | 確認・対処 |
| --- | --- |
| マイク入力バーが動かない | macOSのサウンド → 入力で対象のマイクと入力音量を確認する。「権限」でマイクを確認し、ログ画面の5秒テストを実行する。会議アプリが別のマイクを使っていないかも確認する。 |
| 会議を始めた後に反応しなくなった | 音声形式やデバイスの切り替えで録音エンジンが停止する場合がある。アプリは変更通知と4秒の入力途絶を検出し、30秒に2回まで再接続する。途中の発話は破棄するため、再接続の案内後は合言葉から話し直す。繰り返す場合は会議中のままマイクテストを行い、内蔵マイクなど別の入力も試す。 |
| Macのスピーカーから流れる相手の声に重ねると通らない | 話者優先は同時発話を分離しない。Mac追加音声処理は他アプリの再生音量を下げるため、会議音量を維持したい場合はOFFにする。再生音量を変えずに同時発話を処理する方法は未実装。 |
| 待受を始めると会議のスピーカー音量が下がる | 音声入力 → マイクの詳細 → Macの追加音声処理がONなら、停止してOFFに戻し保存する。必要に応じてアプリを再起動する。システム全体の音量を上げて補正する操作は行わない。 |
| バーは動くが合言葉が通らない | 5秒テストで認識表記を確認し、「音声入力」に別表記を1行ずつ登録する。本人の声の判定を利便性目的で使う場合は「登録した声を優先」を選ぶ。 |
| 短い指示が本人照合で除外される | 厳格モードは1.6秒以上の音声区間を要求する。優先モードは単独・短い発話を拒否せず、区別できる複数話者から登録した声を優先する。 |
| 25秒の発話で停止する | 旧ビルドの挙動。現行版は該当区間を破棄し、次の合言葉の待受を続ける。背景音が続いた後は一呼吸置いて合言葉から話す。 |
| ロック中に送信されない | ロック前に待受を開始し、トークンと権限を確認する。送信前確認ONならロック解除後の確認待ちになる。OSのログアウトや手動スリープとは別。 |
| 対象画面が前面にない | 現行版は画像・OCRを省いて音声の指示だけで続行する。省略を確認画面とログに表示する。画面収録の権限不足は先に解決する。 |
| 音声生成の長さの上限になる | 現行版は改行ごとに独立生成し、160文字を超える行だけ事前分割する。上限に達した未再生区間は再分割し、成功した断片を結合してから再生する。短い音声も生成できない場合は参照音声と全文の一致を確認して試聴する。 |
| モデル未配置・Pythonの案内が出る | 「詳細設定」でローカルパスを確認する。取得が必要ならREADMEのセットアップ用スクリプトを明示的に実行する。通常実行中にはモデルを取得しない。 |
| API Keyの更新画面が出る | 開いたWebexの公式ページでPersonal Access Tokenを取得し、アプリのSecureFieldへ入力する。401の間にブラウザを繰り返し開かない。あとで更新する場合はWebex設定から再表示できる。 |
| キーチェーンのアクセス案内が出る | ホームまたはWebexに表示された「保存済みトークンを読み込む」を押す。「有効性を確認」はパスワードを出す操作ではない。手動でも拒否された場合はキーチェーンのロック状態・署名を確認し、ログの状態番号で切り分ける。macOSの確認に「常に許可」があれば選ぶ。同じ署名を維持し、ACLの書き換えは行わない。 |
| 画面収録を許可しても未許可になる | アプリの起動パス・署名条件を確認し、完全終了して再起動する。署名を変えない。リセットは最初の対処にせず、必要な場合だけ対象を確認してユーザの許可を得る。 |
| 返信待ちが長い | ログの返信候補・途中表示・本文更新を見る。100msはAPI取得後の待ち時間で、最終判定には別に更新停止待ち（初期6秒）がある。429はRetry-Afterを優先する。 |
| 送信結果が不明 | WebexのDMを直接確認する。アプリは重複を避けてPOSTを自動再送しない。 |
| 長文が反復する・発音がおかしい | ビルド8の単語途中の分割をビルド9で修正したが、行内の再分割と少ない先行音声で途切れる報告が残った。ビルド11は冒頭を短く区切り、最初の音声ができ次第再生する。続きは改行ごとに独立生成し、改行のない長文は文末で区切る。試聴欄で問題の文章を送信せず確認する。通常テンプレートの短文改行・カタカナ・数字のひらがな指示と、参照本文が録音の全文に一致することも確認する。 |
| 読み始めるまで遅い | ビルド10では長文の2区間分を生成・再生成してから開始し、準備済みモデルでも約26秒かかった。ビルド11は冒頭の短い区間ができ次第開始する。ログの「準備完了」「返信確定から再生開始」と最初の行の生成秒数を確認する。モデル未準備時の読み込みと、本文更新が止まるまでの待ち時間は別に発生する。 |
| 読み上げの間にノイズが混じる | ビルド12の「参照音声の背景ノイズを軽減」をONにして試聴する。参照録音の背景音が再現されるケースで、静かな部分のノイズ低減を測定した。声の響きが気になる場合はOFFと比較する。音声の継ぎ目・生成待ち・参照録音の背景音は別に切り分ける。[調査記録](speech-quality.md)参照。 |
| 行の間で読み上げが詰まる | ログの「次の行の音声を生成」と「先行音声が尽きた」を確認する。行番号・生成秒数・音声秒数・再生残秒数から、生成待ちが発生したかを区別できる。音声そのものに長い無音や反復が含まれる場合は、このログだけで検出できないため同じ文章を試聴する。 |
| 返信用の合言葉で返信先がない | アプリで直前の最終返信を受け取っている必要がある。「レスポンスを読み上げる」をオンにして通常の送信から確認する。再起動やDM切り替えで返信先は破棄する。 |
| スレッド返信が通常の会話へ出る | 確認画面の「スレッドへの返信」と引用内容を確認する。返信用テンプレートの初期値は新しい文字起こしと会話継続・読み上げ向けの指示。前の回答は送信文に引用しない。実送信のparentIdはテスト対象だが、相手の実動作もE2Eで確認する。 |

音声形式の変更でAVAudioEngineが停止する挙動は[Appleの開発者資料](https://developer.apple.com/documentation/foundation/nsnotification/name-swift.struct/avaudioengineconfigurationchange)を参照してください。会議中の無入力の原因が常にこの変更であるとは限りません。デバイス・音量・追加音声処理・会議中のマイクモードを分けて確認します。

メニューバーは合言葉受領後が赤、送信成功後が緑、次の合言葉の待機中が通常色です。色だけでなくホームの状態表示も確認できます。失敗・取り消し・停止では通常色に戻ります。

## 開発者に不具合を報告する

停止中の「不具合を報告」から、編集可能な下書きを作れます。起動できない場合は `python3 scripts/collect-issue-report.py` を使います。[報告手順](issue-reporting.md)に沿って症状と再現手順を追記し、トークン・宛先・合言葉・会話・録音を含めずに共有してください。リポジトリ内で `$talk-to-webex-bot-report-issue` を使うと、下書きの整理と投稿を支援できます。
